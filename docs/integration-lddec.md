## LDDec 的两个版本（**重要修正**）

调研时按 `Dec/`（Qt + TCP + Faker）描述的行为，与仓库里**实际提交的那份 `dec.exe`**
不一致 —— 它是 `WinDec/` 版。实测确认：

| | TCP 版（`Dec/main_dec.cpp`） | cmd 版（`WinDec/main.cpp`）✅ 仓库里那份 |
|---|---|---|
| 无参数时的 usage 输出 | `Usage: dec <file or path>`（Qt qDebug） | `dec (file or dir)` / `-view`（`std::cout`） |
| 机制 | TCP server 34500 + Faker 进程读文件 | `system('type "文件" > "文件_dec"')` |
| `config.json` | 必需（`port` + `faker`） | **不读** |
| `-view` | 未实现（源码从不看 `argv[2]`） | 已实现 |
| 产物 | `<file>.dec_` | `<file>_dec` |
| 单文件模式 | 无输出 | **无输出**（只有目录模式才打印 `N file(s) decrypted.`） |

实测（本机无绿盾客户端）：`dec.exe <加密文件>` 返回 0、无输出、文件"看起来没变" ——
因为 `type` 读到的仍是密文，`remove + rename` 后内容相同。所以**只能靠产物内容判断
成功与否**，不能靠退出码或输出文本。适配层正是这么做的。

适配层对两者**通用**的部分：自己判断头 3 字节；产物先落临时文件再就地覆盖；单文件
模式不打输出。差异部分（config.json 是否必需）**不做前置检查**，否则会误伤 cmd 版。

## 仍未做的事（按 §2.3 红线）

- 不实现进程伪装 / 冒充白名单进程（那是 LDDec 自带 Faker 的行为，由部署方决定，
  本工具不复刻、也不改名自身可执行文件）；
- 不启用"就地覆盖原文件"的解密模式 —— 交给 dec.exe 的永远是临时副本；
- **不随仓库分发 `dec.exe`**：第三方预编译二进制未经审计，TCP 版还依赖 Qt 运行库。
  改为提供 `packaging/deploy_lddec.py`，由管理员从贵司已部署/已编译的版本拷贝。

§七 的确认问题依旧有效：若能申请到**信任进程白名单**（路径 A），则整条解密链路
不会被触发（工具读到的直接是明文），LDDec 也就不必部署。

## 一、LDDec 是什么

仓库：https://github.com/windywater/LDDec —— 自述为「**天锐绿盾解密工具**」。

### 1.1 核心事实（读源码所得）

| 项 | 结论 |
|---|---|
| 厂商 / 适用对象 | **仅天锐绿盾**（README 原话："仅支持在部署了天锐绿盾系统的机器上运行"）。其他 DLP（亿赛通、绿盾以外产品、Windows EFS、BitLocker、PDF 口令加密）**不适用** |
| 是否"破解"加密 | **不是**。项目内没有任何密钥/算法还原代码。它依赖本机的绿盾客户端 + 文件系统过滤驱动做**透明解密**：受信任进程读文件时驱动返回明文 |
| 加密文件识别 | 文件**头 3 字节**等于 `\x88\x7d\x1c`（`Dec/main_dec.cpp` 的 `kEncryptedTag`）即判定为加密文件；`-view` 模式只判断不解密 |
| 语言 / 依赖 | C++ + **Qt**（QtCore / QtNetwork）。`Dec.sln`（MSVC）+ `LDDec.pro`（qmake）；Windows x64 与 Linux 各一份二进制（`dec.exe` 40KB、`dec_linux` 352KB，动态链接 Qt，需 Qt 运行库） |
| 目录结构 | `Dec/`（TCP server 主程序）、`Faker/`（读文件的客户端）、`WinDec/`（另一版，用 `type file > tmp` 走 cmd 读取）、`Common/`（配置 + TCP 分块读写） |

### 1.2 工作原理（关键，决定能不能用）

```
dec.exe（server, 监听 127.0.0.1:34500）
   └─ 启动同目录下 config.json["faker"] 指定的进程（默认 notepad.exe，即编译出的 Faker 改名）
Faker（client）
   └─ 连回本机 34500；收到"文件名"→ 用普通文件 API 读该文件
        → 绿盾驱动识别该进程为受信任进程，读出的就是明文
        → 把明文按 10KB 分块回传给 dec.exe
dec.exe
   └─ 写入 <原文件>.dec_，复制原文件时间戳，然后删除原文件、改名覆盖
        → 结果是【密文文件被就地替换成明文文件】
```

`WinDec` 是简化版：用 `type "文件" > "临时文件"` 借 cmd.exe（若 cmd 在白名单内）拿到明文后同样覆盖原文件。

**结论：解密能力 100% 来自"本机绿盾客户端 + 该进程被信任"，与文件格式无关。**

### 1.3 输入 / 输出

- **输入**：单个文件路径，或目录（目录模式会遍历其中**所有**文件）
- **输出**：**就地覆盖**——原文件变成明文（`Dec` 版写 `.dec_` 后替换；`WinDec` 版写 `_dec` 后替换），时间戳保留
- **退出**：无 API、无结构化返回码，只有 `qDebug()` 打印；`-view` 在 `Dec/main_dec.cpp` 中**并未实现**（README 与代码不一致，只有 `WinDec` 版有）
- **无库形态**：没有导出函数/头文件/SDK，只有可执行文件和一条**私有本地 TCP 协议**
  （`int32 文件名长度 + 文件名` → `int64 明文长度 + 明文流`；`int32 = -1` 表示结束）

### 1.4 可集成方式评估

| 方式 | 可行性 | 说明 |
|---|---|---|
| 作为库链接 | ✗ | 不存在库产物，无公开 API |
| 源码级嵌入 | ✗ | C++/Qt，与本项目（Python + Tkinter）跨语言；且 TCP server/client 双进程结构难以内联 |
| **命令行调用** | △ | 唯一现实入口（`dec.exe <文件>` / `-view`）。但**默认行为是覆盖原文件**，直接调用会破坏加密状态 |
| 重写其 TCP 协议（自己做 client） | ✗（不建议） | 协议私有无版本承诺；且该路径等价于自己实现"伪装成受信任进程去读文件"，见 §2.3 合规红线 |

## 二、能否还原被加密的 PDF / 图片

### 2.1 能 —— 的前提（**四条必须同时成立**）

1. 执行机器**已安装并运行天锐绿盾客户端**（驱动在生效）
2. 当前登录用户**对该文件有解密授权**（DLP 通常按用户/部门策略授权；无授权时驱动不解密，读出仍是密文）
3. 读取进程在驱动看来是**受信任进程**（白名单）
4. 文件确实是**绿盾加密格式**（头 3 字节 `88 7D 1C`）

### 2.2 限制

- **与文件格式无关**：加密标记在文件头，PDF / JPG / PNG / TIFF… 一视同仁。因此适配层要覆盖的是工具现有的**全部**扩展名（`IMAGE_EXTS` + `.pdf`），不是某一类。
- **目录模式危险**：`dec.exe <目录>` 会把目录下所有加密文件都解密并覆盖，绝不能对"用户选择的输出目录"或任意目录调用。
- **明文落地即破防**：解密后文件长期以明文存在磁盘上，等于绕过了 DLP 的静态保护。
- **PDF 口令加密是另一回事**：若 PDF 是标准口令加密（`%PDF` 头正常、打开要密码），绿盾无关，应走 PyMuPDF 的密码参数，不在本方案范围。
- **无版本号/兼容性承诺**：17 次提交、单人维护、最后一版 2025-12；绿盾客户端升级或策略调整后可能失效。
- **二进制可信度**：仓库直接提交了 `dec.exe`，需自行用源码编译并审计，不能拿现成二进制投放到内网。

### 2.3 合规红线（必须先解决，否则不建议实施）

`Faker` 组件的做法是：**把可执行文件命名为 `notepad.exe`（`config.json.faker` 可配），冒充白名单进程让驱动吐明文**，再通过本地 TCP 把明文交给另一个进程。这是**绕过管理员设定的进程白名单策略**，不是"使用官方授权的解密接口"。

由此产生两个我不建议直接实施的点：

- 我不会实现"进程名伪装 / 冒充受信任进程"的代码；
- 也不会让水印工具调用"**就地覆盖原文件**"的解密模式（与本项目"绝不覆盖原文件"的契约直接冲突，且会永久破坏加密状态）。

正确顺序是：**先拿到授权（把水印工具本身加进白名单），再谈代码**。见 §3。

## 三、两条路径，建议走第一条

### 路径 A（推荐）：把水印工具加入绿盾信任进程白名单 —— **零代码改造**

- 做法：向信息安全/绿盾管理员申请，将 `WatermarkTool.exe` 加入"信任进程/白名单"。
- 效果：工具用现有代码 `Image.open` / `fitz.open` 读文件，驱动自动返回明文，**整条链路无需任何改动**；输出新文件时驱动也会自动加密，加密状态闭环。
- 适用：绝大多数企业内网场景，这才是 DLP 厂商设计的正道。
- 若获批，本方案只需保留 §5.1 的"加密文件检测 + 友好提示"（告诉用户"此文件受保护，请在已授权环境打开"），其余不必做。

### 路径 B：水印工具内置"透明加密适配层"（仅在拿不到白名单、但有书面授权时）

- 前提：**信息安全部门书面授权**指定解密手段（可能是绿盾官方 SDK、内部合规解密服务，或批准使用某个解密器）。
- 形态：工具只依赖一个「**解密提供者**」抽象（配置项/环境变量），**不内置也硬编码任何具体解密器**，更不内置进程伪装逻辑。
- 行为铁律：
  1. **绝不覆盖原文件**（沿用现有契约）
  2. **明文只写入受控临时目录**，用完立即删除（含异常/取消路径）
  3. 输出文件名仍为 `原名_水印版.扩展名`，加密状态由驱动自行决定
  4. 默认关闭，需显式开启

## 四、集成位置与调用流程（路径 B）

### 4.1 介入点：**文件加载 / 解析阶段**（唯一合理位置）

原因是现有代码在 3 处按路径打开文件，全部集中在 `wm/media.py`：

- `Document.__init__`：图片 `Image.open(self.path)`、PDF `fitz.open(self.path)`
- `Document.page_image()`：图片会 `with Image.open(self.path)` 再次按路径打开
- `kind_of()`：目前**纯按扩展名**判断类型（加密文件扩展名不变，所以这层不受影响，但后续若要做"内容嗅探"需在此扩展）

因此适配层的正确姿势是：**在构造 `Document` 之前把"可读的明文路径"解析出来**，让后续所有读取都走明文路径。

### 4.2 目标流程

```
用户添加文件
   ↓
wm/dlp.py: probe(path)                # 只读前 3~8 字节，开销可忽略
   ├─ 非加密文件      → 直读（现状，零开销）
   ├─ 加密 + 可读明文 → 走明文（可能是驱动直接给的，或解密器输出的临时文件）
   └─ 加密 + 不可解密 → 标记状态，交给 §5 降级策略
   ↓
Document(plaintext_path)              # 后续渲染/预览/批处理完全不感知
   ↓
处理完成 → finally: 清理临时明文
```

### 4.3 需要覆盖的文件类型

**全部现有支持类型**：`.png .jpg .jpeg .bmp .webp .tif .tiff .gif .pdf`。
加密标记与格式无关，按类型开白名单只会漏。

### 4.4 关键改动点清单

| # | 文件 | 改动 | 说明 |
|---|---|---|---|
| 1 | **新增 `wm/dlp.py`** | `EncryptedFile` 异常类；`is_encrypted(path)`（魔数检测）；`resolve_plaintext(path)` → 返回 `(可读路径, 是否临时, 原因)`；`TempPlaintext` 上下文管理器负责清理 | 唯一与"加密"打交道的模块；解密器通过配置项注入，**不硬编码** |
| 2 | `wm/media.py` | `Document.__init__` 增加可选 `read_path` 参数（默认 `= path`）；`self.path` 保留原始路径用于输出命名，`self.read_path` 用于所有实际读取（`Image.open` / `fitz.open` / `page_image`） | 这是改动量最小、最不容易出错的切法；`kind_of` 不动 |
| 3 | `wm/spec.py` | 新增 DLP 配置字段：`enable`（默认 False）、`magic`（默认 `88 7D 1C`，可配）、`decrypt_cmd` 模板（形如 `"{exe}" "{src}" "{dst}"`，由管理员配置/环境变量覆盖） | 不把第三方 exe 路径写死在代码里 |
| 4 | `wm/ui/app.py` | `_add_paths()` 加入文件后做一次快速探测，列表/状态栏提示"N 个文件受加密保护"；预览前调 `resolve_plaintext` | UI 只做提示与编排，不含解密逻辑 |
| 5 | `wm/ui/preview_job.py` | `render_preview` 入口先 `resolve_plaintext`，用 `with` 保证退出即清理 | 预览是单帧，最容易泄漏临时文件 |
| 6 | `wm/ui/batch.py` | `run_batch` 循环内：先预检扫描（统计受保护文件数）→ 逐文件 `resolve_plaintext` → 处理 → `finally` 清理 | 必须保证取消 / 异常 / 单个文件失败都不残留明文 |
| 7 | `wm/ui/output.py` | 输出路径仍由 `media.plan_output(原路径, ...)` 计算；确认输出目录**不落在**临时解密目录 | 防止把明文产物写到临时目录被清理 |
| 8 | `tests/test_dlp.py` | 用假解密器（写临时文件的小脚本）覆盖：魔数识别、明文解析、临时文件清理、解密失败降级、批处理中途取消不残留 | 现有 77 用例之外新增，不动既有断言 |
| 9 | `README.md` / `AUDIT.md` | 记录能力边界、授权前提、配置项 | — |

### 4.5 调用流程细节（批处理）

1. **预检**：遍历文件列表，`is_encrypted()` 只读头部，统计 `加密文件数`，进度文案分两段（"解密中 3/10" → "加水印 4/10"）。
2. **按需解密**：同一源文件在一批任务内只解密一次，明文临时文件路径进 `SizedLRU`（复用 §第二批已落地的缓存，key = 原始路径 + mtime + size）。
3. **处理**：`Document(read_path=明文路径)`，渲染链路完全不变。
4. **清理**：`finally` 中删除临时明文；进程退出前做一次全局清理（防止崩溃残留）。

## 五、降级策略与错误提示

### 5.1 分级处理

| 情况 | 行为 | 用户看到的提示 |
|---|---|---|
| 非加密文件 | 正常处理 | — |
| 加密 + 当前进程已被信任（白名单生效） | 直读明文，无提示 | — |
| 加密 + 解密器不可用（未配置 / exe 缺失 / 非绿盾机器） | **跳过该文件，批处理继续** | "xxx.pdf 受加密软件保护，当前环境无法解密，已跳过。请联系信息安全部门为水印工具授权。" |
| 加密 + 解密器报错 / 超时 | 跳过并计入失败列表 | "xxx.png 解密失败（<原因>），已跳过。" |
| 加密 + 用户对文件无授权 | 跳过 | "xxx.docx 你没有解密权限，已跳过。"（驱动返回仍为密文 → 解析失败 → 归入此类） |
| 全部文件都无法解密 | 批处理不启动，直接给出汇总 | "所选 N 个文件均受加密保护且无法在当前环境解密，未产生任何输出。" |
| 预览单个加密文件失败 | 预览区显示占位提示，**不弹错误框** | "此文件受加密保护，无法预览；加水印时同样会跳过。" |

### 5.2 铁律

- **任何情况下都不覆盖、不改写原文件**（现有契约，适配层不得破坏）
- **失败不静默**：跳过的文件必须在结果面板/日志里逐条列出，不能只报"成功 N 个"
- **超时保护**：解密器调用设超时（建议 30s/文件），避免驱动无响应时整个批处理挂死
- **临时文件不进输出目录、不复用文件名**（用随机名 + `.tmp` 后缀，落在 `%LOCALAPPDATA%\WatermarkTool\dldec\`）

## 六、风险

| 类别 | 风险 | 缓解 |
|---|---|---|
| **合规（最高）** | LDDec 的 `Faker` 靠**冒充白名单进程**（改名 notepad.exe）取明文，属绕过管理员策略；可能违反公司信息安全制度与绿盾许可条款 | 优先走路径 A 申请白名单；路径 B 必须有书面授权 + 记录审批号；**不实现进程伪装** |
| **数据安全** | 明文落盘、崩溃/取消后残留；`dec.exe` 默认行为是**就地覆盖原文件**永久破坏加密 | 明文只写受控临时目录；`finally` + 退出钩子双清理；不调用覆盖模式；临时目录权限收紧到当前用户 |
| **兼容性** | 仅天锐绿盾有效；客户端版本/策略变更会导致魔数或行为变化；`dec.exe` 依赖 Qt 运行库；仓库二进制不可信 | 魔数与解密命令均可配；用源码自行编译并审计；集成时先做"探测-only"灰度 |
| **性能** | 每文件一次进程启动 + 全量 IO；本地 TCP 34500 端口可能被占用/拦截；大批量显著变慢 | 预检 + 按需解密 + 批内缓存；超时与并发上限（仍串行）；进度条分段反馈 |
| **密码学/正确性** | 若判断错"是否加密"会误处理；明文与密文长度不同不能按原偏移读 | 以魔数 + 解析双重校验（拿明文后仍要走一次 `Image.open`/`fitz.open` 验证） |
| **维护性** | 依赖单人维护、无版本承诺的第三方项目 | 抽象成"解密提供者"接口，可随时换成官方 SDK 或内部服务，业务代码不感知 |

## 七、需要你确认的问题（回答前不进入实现）

1. **贵司的加密软件是否就是"天锐绿盾"？版本号是多少？** —— LDDec 只对该厂商有效；若不是，需要另外定位（请提供加密文件的**前 16 字节十六进制**和一款能正常打开它的受信任程序名）。
2. **能否直接把 `WatermarkTool.exe` 加入绿盾信任进程白名单？** —— 若可以，走路径 A，基本零改造，我建议就到此为止。
3. **绿盾是否提供官方 SDK / 解密接口 / 外发审批流程？** —— 有官方渠道时不应使用第三方工具。
4. **是否有信息安全部门的书面授权**允许在工具内做"解密→加水印→重新加密"？授权范围（哪些目录/哪些文件/哪些用户）？
5. **输出文件的期望状态**：加水印后的新文件，驱动会自动加密吗？（通常新建文件会被自动加密，需实测确认）明文输出是否被允许？
6. **文件来源**：本地磁盘 / 网络共享 / 文档管理系统？（驱动钩子与授权策略在不同路径上表现不同）
7. **部署约束**：能否随工具分发第三方 exe？能否要求安装 Qt 运行库？目标机器 Windows 版本？
8. **规模**：单批文件数量与单文件大小的典型量级（决定是否需要并发与超时调优）？

## 八、建议的决策顺序

1. 先回答 §7 的 1、2、3 —— 大概率答案是"可以加白名单"，那么 **不需要 LDDec，也不需要改代码**，本方案可归档。
2. 若确实拿不到白名单且拿到书面授权 → 走路径 B，按 §4.4 清单实施，**第一批只做 §5.1 的检测与提示（只读、零风险），确认有效后再做解密链路**。
3. 无论哪条路，`dec.exe` 的**覆盖原文件模式**都不启用；`Faker` 的进程伪装不实现。
