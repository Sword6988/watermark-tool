# 图片 / PDF 文字水印工具（Windows 桌面版）

一款纯本地、无网络的 Windows 桌面小工具：给图片与 PDF 添加**文字水印**。
**水印始终以平铺方式铺满整个页面，位置由系统固定、不可调节**；支持实时所见
即所得预览与批量处理。

技术栈：Python + Tkinter（自绘 Fluent 浅色主题）+ Pillow（图片）+ PyMuPDF（PDF）。

---

## 一、运行

必须使用**系统 Python**（WorkBuddy 托管 Python 没有 tkinter）。下面用
`<PY>` 代指你的系统 Python 实际路径，例如官方安装器默认是：

```
set PY="%LOCALAPPDATA%\Programs\Python\Python313\python.exe"
```

（若是「为所有用户安装」，则在 `C:\Program Files\Python313\python.exe`。
全项目统一 **Python 3.13**；换个机器请把 `<PY>` 换成那台机器上的真实路径。）

```
<PY> main.py                 # 打开空窗口
<PY> main.py a.png b.pdf     # 启动时预载文件
```

依赖清单见 `requirements.txt`：`Pillow`、`PyMuPDF`、`numpy`（测试用）、
`tkinterdnd2`（拖拽）、`PyInstaller`（打包用）；`tkinter` 为标准库。
除打包外，运行本工具**不需要** `pip install`。

## 二、功能

- **导入**：把文件/文件夹直接**拖进窗口**，或点「选择文件」多选。
  支持图片 `png/jpg/jpeg/bmp/webp/tif/tiff/gif` 与文档 `pdf`。
- **文件列表**：可单选查看、删除选中项、一键清空。
- **平铺铺满整页（固定行为）**：水印按「首尾贴齐 + 整轴均分」的网格铺满整页，
  **没有开关、没有位置偏移、没有拖拽定位**，也**不支持单独设置某一个水印**。
  疏密由「字号 / 四周边距 / 旋转角度」决定。
- **实时预览**：右侧画布自适应缩放，参数一改立即刷新；显示「原图 W×H / 预览比例」。
  PDF 默认第 1 页，可翻页。预览**只用于查看**，不接受拖拽等位置交互。
- **批量导出**：对列表全部文件逐一处理，带**进度条**与**取消**；批处理期间左栏
  参数整体冻结（避免预览线程与批处理争抢同一份内存）。
- **输出**：默认与原文件同目录，文件名加 `_水印版` 后缀，也可另选输出目录。
  **绝不覆盖原文件**，同名自动加 `(1)`/`(2)` 序号；失败会明确报出「哪个文件、什么原因」。
- **元数据跟随**：输出图片保留源图的 EXIF 朝向、**DPI** 与 **ICC 色彩配置** ——
  丢掉 DPI 会让 300dpi 的扫描件打印尺寸放大 4 倍，丢掉 ICC 会偏色。
- **一键恢复默认**：参数标题栏右侧的「恢复默认」把全部参数拽回出厂值。

## 三、参数语义表

**统一度量：所有尺度参数都是「页面短边百分比」**，`ref = min(页面宽, 页面高)`。

| 参数 | 控件 | 范围 / 步进 | 默认 |
|---|---|---|---|
| 水印文字 | 多行文本 | 支持回车换行 | 机密文件 |
| 字体 | 下拉 | 自动发现系统字体，**微软雅黑优先**（鸿蒙黑体排在其后：多数机器没装它，占首位只会让下拉框首选项落空）；**显示中文名**，渲染仍用英文原名；**能排中文的排前面**，西文排后面 | Microsoft YaHei |
| 字号 % | 滑块 + 数字 | 0.5 – 30，步进 1 | 4.0 |
| 四周边距 % | 滑块 + 数字 | 0 – 20，步进 1 | 3.0 |
| 旋转角度 | 圆盘 + 数字 | −180 – 180°，步进 1（循环量：360° 即 0°，350° 归一为 −10°）；**顺时针为正**（与时钟同向） | 30 |
| 不透明度 % | 滑块 + 数字 | 5 – 100，步进 1（内部仍存 0.05 – 1.00 的 alpha） | 30 |
| 颜色 | 预设色色块（6 种） | 仅预设色，无自定义取色 | #d32f2f |

> 数字框越界输入（如不透明度输 200）自动**钳制到最近边界**，不会报错中断；
> **旋转角度例外** —— 它是循环量，越界按取模归一（输 360 得 0，输 350 得 −10），
> 因为把它夹到边界会**改变方向**（350° 几乎水平，夹成 180° 就完全倒置了）。
> 字体下拉弹出列表的滚动条与面板右侧滚动条共用同一套样式（宽度 / 圆角 / 轨道 / 悬停与按下色）。

> **没有「平铺」开关**：平铺是唯一且固定的行为；**也没有位置偏移参数**
> （界面不提供 X / Y 偏移、重置居中、预览拖拽等任何调节入口）。

换算：

```
font_px   = 字号%   / 100 × ref
margin_px = 边距%   / 100 × ref
```

> 因为一切都是「短边百分比」，预览把页面等比缩小后**全部参数自动等比**，
> 视觉与最终输出完全一致（无需任何额外补偿系数）。

### 「四周边距」的含义（只有平铺一种语义）

每个水印四周的留白；相邻水印之间的可见空隙 **不小于** `边距 × 2`（实际按页面
均分，只会略大，见 [已知限制 2](#八已知限制)）。

界面提示文案：`每个水印四周留白`。

## 四、操作说明

1. **加文件**：拖入窗口，或点「选择文件」。两条入口都会在文件进列表前**自动完成
   解密探测**（见 §十一），用户没有任何额外的手动步骤。
2. **改参数**：左栏拖动/输入，右侧预览即时更新（约 150 ms 防抖）；改乱了点标题栏
   右侧的「恢复默认」。
3. **输出**：可选输出目录（或「恢复同目录」），点「开始添加水印」，
   看进度条；中途可「取消」。输出文件名自动加 `_水印版` 后缀。

> 水印**不需要也不能调位置**：它始终平铺铺满整页，位置由系统按页面尺寸与
> 「字号 / 边距 / 角度」算出，界面不提供任何位置入口。

## 五、设计要点（为什么这么做）

1. **唯一版式权威 `wm/layout.py`**：块几何（含墨迹 bbox）与平铺起止序列都只在这里
   算一次，图片与 PDF 两条渲染路径**消费同一份布局结果**——各自算一遍必然产生
   像素偏差。**平铺是唯一的版式**，这里没有任何「单块定位 / 偏移」分支。
2. **平铺算法 = 完整水印 + 首尾贴齐 + 整轴均分**（`axis_starts`，v3）：
   - 设 `span = 页面边长 − 2×边距 − 墨迹边长`（墨迹可用跨度）、
     `step = 墨迹边长 + 2×边距`（保证 `边距×2` 可见空隙所需的最小步长）；
   - `k = ⌊span / step⌋`（在满足最小间距前提下取**最大块数**，`k ≥ 1`）；
     令 `g = span / k`，墨迹起点序列 = `边距 + i×g`（`i = 0 … k`）；
   - 结果：**首块贴左边距线、末块贴右边距线（首尾贴齐），同轴所有间隙严格相等
     （整轴均分）**，且 `g ≥ step` ⟹ **可见空隙 `= g − 墨迹 ≥ 2×边距`**
     —— 全参数网格下**既不粘连也不重叠**；
   - **代价**：实际间隙可能比名义步长**大最多 `(k+1)/k` 倍**（把 `floor` 的余量摊到
     每一段，是均分法的必然结果，属规格内行为）；
   - **退化**：`span ≤ 0`、`step ≤ 1px` 或 `k < 1`（只放得下一块）时**只放一块并居中**，
     不抛异常；`MAX_TILES = 4000` 时以 `extra_gap` 倍增步长回退，仍收敛。

   > **为什么不再用「等距排满 + 末列补齐」（v2 已废弃）**：那条路先按 `floor` 排满，
   > 再把最后一块「补」到边距线上，而 `floor` 后的余量恒 `< step`，补出来的末块
   > **起点差必然 `< step`**；若守卫把判据误写成「起点差 ≥ 2×边距」（正确判据是
   > **可见空隙 = 起点差 − 墨迹 ≥ 2×边距**），末块可见空隙就会小于设定值，极端参数
   > 下甚至为**负（墨迹重叠）**。实测 A4 595×842、font=4%、margin=1%：末两行起点差
   > 仅 18.1 < 墨迹高 63，重叠 44.9 px。均分法彻底消除此缺陷。**不要再改回补齐式。**
3. **渲染层三入口（v4）——「墨迹锚点」摆放是缩放协变的关键**：
   - **`wm/render.py::_render_crisp_layer`（输出核心）**：版式**恒按原生（1:1）页面坐标
     计算**，只有块位图按 `scale` 光栅化；位图先**裁到自身墨迹 bbox**、精确拉伸到
     `round(墨迹 × scale)`，再按**墨迹锚点**回贴：`blit = (块左上角 + 墨迹偏移) × scale − 缩放块墨迹偏移`。
     于是墨迹落点恒等于「页面坐标布局 × scale」，与 `block_padding` 的 2px 硬下限、
     字号取整**完全无关**。
   - **为什么必须裁+拉伸而不能只对齐一条边**：FreeType 的字形外接框**并非严格线性缩放**
     （实测 A4 font4%：原生墨迹宽 89 → 2× 实际 174 ≠ 178），只按「缩放块自身 bbox」对齐
     会让对面边漂移约 2pt，破坏「贴边 ≤2px」。
   - **为什么版式不在缩放坐标系里重算**：`axis_starts` 里 `k = ⌊span/step⌋` 是**不连续**的，
     缩放坐标系的取整误差会让 `span/step` 跨过整数边界 → 块数变化（实测 900×600 /
     font4% / m3% / 45°：1× 得 6 列、2× 得 7 列），图片与 PDF 的平铺网格就不一致了。
   - **两个对外入口**：`render_output_layer`（输出，图片超采样 `RENDER_SCALE = 2.0`、
     `PDF_RENDER_SCALE = 2.0`，两条路径同一光栅倍率 → 水印逐像素一致；超采样顺带把
     1x 直栅化被抗锯齿衰减的最外 2–3px 补回来）；`render_overlay_layer`（**预览** =
     整层 1:1 渲染后整体缩放）→ **预览与输出逐像素同构**（实测 24 组合 bbox 偏差
     0.0000%、覆盖率差 0.000pp、IoU = 1.0000）。
   - > 教训（v3 的真实缺陷，勿回退）：v3 按未缩放的块左上角摆放、却按缩放字号光栅化，
     > 小页面 / `scale` 偏离 1 时墨迹漂移 3.2–4.6px、320×240+边距1% 顶行**触边被裁**，
     > 预览密度与输出差 3.7–5.8pp。
4. **PDF 输出**：每页插入**一张**按页面尺寸缓存的透明层
   （`page.insert_image(page.rect, pixmap=pix, overlay=True)`），而不是几千次矢量
   文字绘制。**alpha 保留已实测并写进回归测试**（若丢失会表现为「整页被不透明层盖住」）。
5. **测墨迹 bbox 用不透明度=1.0 的探针**：低不透明度会抹掉边缘抗锯齿像素，测出的
   墨迹比实际小，进而让间距偏大。
6. **块内边距压到最小** `max(2, 行高 × 0.08)`：仅用于规避旋转重采样在块边缘的
   抗锯齿裁切；留白过大在 30° 下会被放大，让平铺变稀疏。
7. **UI 线程模型**：预览与批处理都在后台线程；后台线程**绝不直接调用 Tk**，结果
   进 `queue.Queue`，主线程 `after()` 轮询后贴图；预览用 generation 计数丢弃过期帧
   （打开坏文件失败时也会取消在途预览并作废代数，避免过期 worker 覆盖错误占位）。

## 八、已知限制

1. **多帧图片（动画 GIF / 多页 TIFF）只处理首帧**，输出为单帧文件；处理日志会标注
   「仅首帧（共 N 帧）」。
2. **平铺时相邻水印的可见空隙「不小于」`边距 × 2`，最多可比名义步长大 `(k+1)/k` 倍**。
   整轴均分保证零重叠、零裁切、间距完全均匀，代价是实际间距略大于设定值。
   这是 v3 的规格内行为（替代 v2「末列补齐」导致末行间隙过小/重叠的缺陷）。
3. **像素级墨迹检测在 30° 旋转下有 ≤2 px 的测量偏差**（旋转重采样让字形斜角尖端的
   抗锯齿像素被判墨阈值滤掉），属测量偏差而非摆放偏差；摆放本身由几何计算保证。
4. 预览的 PDF 页面按显示分辨率栅格化（非矢量），缩放到很大时字会有轻微模糊；
   最终输出始终是全分辨率的。
5. 输出图片格式沿用原扩展名；JPEG / BMP / GIF 会压平 alpha（白底）。
   元数据（EXIF / DPI / ICC）按目标格式能力写回：BMP / GIF 没有这些容器，会跳过；
   任一项写失败也不会让导出失败，只在 `runtime-<pid>.log` 记一行降级提示
   （日志在 `%LOCALAPPDATA%\WatermarkTool\logs\`，按进程分文件，只留最近 5 份）。
6. **PDF 输出的光栅倍率按页面大小自适应**：A4 及以内仍用 2×（144dpi，打印清晰），
   A0 这类巨页自动降到 1× —— 固定 2× 时 A0 单页要 2.44s、体积 +873KB，降倍率后
   回落到 +305KB / 0.6s，而**版式（块数、间距、贴边）完全不变**。
7. 透明底 PNG 加水印后**透明区域保持透明**（已实测角落 `alpha=0`）；在部分看图软件里
   透明区会被渲染成黑/白棋盘底，那是查看器的显示方式，输出文件本身没问题。
8. 界面仅在 Windows 上验证（依赖 DPI 感知与 `tkinterdnd2` 拖拽）。
9. **加密文件（DLP / 透明加密）能否处理，取决于运行环境**：工具只负责「探测 → 调
   用已授权的解密器 → 用明文出图」。没有可用的解密手段时，该文件会被跳过并给出
   明确原因，不会静默失败，也不会影响同批其它文件。详见 §十一。
10. **带打开口令的 PDF 不支持**：这类文件设有「打开密码」，工具读不到任何页面
    内容。添加时会直接拒绝并提示「该 PDF 设有打开口令，需要密码才能读取 ——
    请先用其它工具解除口令保护，再添加此文件」，不会静默失败、也不会等到导出才
    炸。只设了**所有者口令**（限制打印 / 编辑但允许直接打开）的 PDF 不受影响，
    可以正常处理。

## 十、打包与分发（两种形态，**对外只发单文件版**）

> **当前交付形态 = 单文件版 `dist/WatermarkTool.exe`。**
> 目录版（`dist/WatermarkTool/` + portable.zip）自 2026-09-27 起**不再产出、不再分发**，
> 已构建的旧产物已移入 `_trash/`。打包脚本 `packaging/build.py` 与
> `packaging/watermark-dir.spec` **保留**，需要调试时仍可自行构建，
> 但不要把它发给用户——两个形态并存最容易出的事故是**发错包**或**丢 `_internal` 导致起不来**。

两种包**功能完全一致**，都由同一份源码、同一套 `spec_common` 依赖清单构建，
区别只在「文件怎么摆」：

| | 单文件版 | 目录版 |
|---|---|---|
| 产物 | `dist/WatermarkTool.exe`（1 个文件） | `dist/WatermarkTool/`（`WatermarkTool.exe` + `_internal/`） |
| 分发 | 发一个文件即可 | 必须整个文件夹打包，丢掉 `_internal` 就起不来 |
| 体积 | 32.2 MB（已压缩） | 68.4 MB 展开 / 32.1 MB zip |
| 冷启动 | ≈1.6 s（每次解压到 `%TEMP%\_MEIxxxxxx`） | ≈0.6 s（直接读 `_internal`） |

> 上表的体积 / 冷启动是**早期基线**（dec.exe 入包之前测得，且随 PyMuPDF / Pillow
> 版本变化），只用于两种形态之间的**相对比较**，不要当作当前版本的验收指标。
> 需要准确数字时以当次构建脚本的实打输出为准。
| 退出 | 自动清理临时解压目录 | 不留临时文件 |
| SmartScreen | 相对更容易被拦 | 相对少见 |

构建（必须用装了 PyInstaller + 本项目依赖的**系统 Python**，托管 Python 没有 tkinter）：

```
python packaging/build_onefile.py    # 单文件版：dist/WatermarkTool.exe   ← 交付用这个
python packaging/build.py            # 目录版：  dist/WatermarkTool/ + portable.zip（仅调试，不分发）
```

两个脚本都会**构建 → 自检（tkdnd / 图片 / PDF / 中文路径）→ GUI 冒烟 → 出 md5**，
任何一步失败即拒绝交付。单文件版另有独立验收：

```
python _smoke/verify_onefile.py                              # 单文件版
python _smoke/verify_onefile.py dist/WatermarkTool/WatermarkTool.exe   # 目录版对照
```

它把 exe **单独拷进空目录**运行，断言：自检全过、冷启动秒数被量化、
`%TEMP%\_MEI*` 自解压目录确实生成（目录版则断言**不**生成）、程序目录无旁挂文件。

单文件版的实现只有最后一步不同：`EXE()` 把 `a.binaries + a.datas` 全塞进 exe、
不生成 `COLLECT`。源码零改动 —— 运行时 `sys._MEIPASS` 就是解压目录，
`main.module_root()` 本就优先读它，图标 / tkdnd / PyMuPDF 的 DLL 都从那里加载。

## 十一、加密文件（DLP / 透明加密）自动解密

内网加密软件（如天锐绿盾）把文件以密文写在磁盘上，直接解析必然失败。工具内置一层
**解密适配层**（`wm/dlp.py`）：文件在**进入列表之前**就被换成"可读的明文路径"，
预览、渲染、批处理整条链路都不知道加密这件事。

解密用的是**多通道回退链**（`wm.dlp.ChainProvider`），按序尝试、任一成功即用：

| 顺序 | 通道 | 需要什么 | 说明 |
|---|---|---|---|
| 1 | **LDDec**（`dec.exe`） | 程序目录下有 `dec.exe` | 面向天锐绿盾的专用工具，已随包分发 |
| 2 | **cmd 读取** | Windows 自带 | `cmd /c type`，LDDec 的 WinDec 版就是这么做的 |
| 3 | **PowerShell 读取** | Windows 自带 | `[IO.File]::ReadAllBytes`，不受中文路径影响 |

后两条让工具在**完全没有第三方二进制**的机器上也有机会解出明文 —— 前提是管理员把
`cmd.exe` / `powershell.exe` 放进了信任名单。三者都不行才会跳过文件并给出原因。

每一环都以**产物内容**判定成功（不是"命令返回 0"）：返回 0 但读到的仍是密文的情况
非常常见，只有内容对了才往下游交。

### 触发时机（只有一处）

```
「选择文件」按钮 ─┐
                  ├─→ App._add_paths() ─→ dlp.resolve(每个文件) ─→ 进列表
拖拽投放 ─────────┘
```

`_add_paths` 是两个入口的**唯一汇聚点**，解密只挂载在这里，因此两条路径行为必然
一致，也不需要任何手动解密步骤。命令行传入的文件（`main.py` 的 argv）同样走这里。

### 判定顺序

| 情况 | 处理 | 用户看到 |
|---|---|---|
| 文件头不是加密魔数 | **原样进入列表**，零额外开销 | 无（与接入前完全一致） |
| 命中魔数，但按原路径**能打开** | 按原样继续（透明解密已生效 / 魔数误判） | 状态栏提示 N 个文件疑似受保护 |
| 命中魔数、读不开、**有解密器** | 解密到受控临时目录 → 校验产物 → 用明文 | 无 |
| 命中魔数、读不开、**无可用通道** | 跳过该文件 | 「受加密保护，当前环境无法解密（本机没有可用的解密组件）」 |
| 解密器报错 / 超时 / 产物损坏 | 跳过该文件 | 「xxx.png：解密超时（超过 30 秒）」等具体原因 |

批量时失败只影响它自己：其余文件照常进列表，失败项在**一个**汇总框里逐条列出，
不会循环弹框把界面堵死。

### 部署 LDDec（第一通道，随包分发）

仓库的 `tools/LDDec/dec.exe` 已随包分发（来源：贵司另一款工具 `price-tool` 中已
验证可用的那份，cmd 版 / WinDec，无 Qt 依赖），**开箱即用** —— 启动后状态栏会显示
「已启用解密通道：LDDec（dec.exe）、cmd 读取、PowerShell 读取」。
若要用别的版本替换，或本机已有一份：

```
python packaging/deploy_lddec.py --from D:\Tools\LDDec    # 从已有目录
python packaging/deploy_lddec.py --from D:\Tools\dec.exe  # 只给一个 exe 也行
python packaging/deploy_lddec.py --check                  # 检查是否已被识别
```

换版本时 `deploy` 会一并重写 `tools/LDDec/SHA256.txt`（记录来源、生成时间与
SHA256）；`--check` 会核对指纹。`tests/test_entrypoint.py` 把「二进制与清单一致」
做成用例 —— 换了二进制却没更新清单，回归会直接失败。溯源记录另见
`docs/integration-lddec.md` 的「随包分发的 `dec.exe`」一节。

自动搜索顺序：`WM_LDDEC_EXE` → 程序目录下 `LDDec/`、`tools/LDDec/`、程序目录本身、
`tools/lddec/`。打包时 `tools/LDDec/` 会**原样收进** exe（冻结后落在
`sys._MEIPASS/tools/LDDec/`）。

#### 两个版本都支持

LDDec 有**两套**实现，二进制都叫 `dec.exe`，命令行用法相同（`dec.exe <文件或目录>`），
适配层两者都支持：

| | TCP 版（`Dec/`） | cmd 版（`WinDec/`）——**仓库里提交的那份就是它** |
|---|---|---|
| 机制 | 起 TCP server + Faker 进程读文件 | `cmd /c type "文件" > "文件_dec"` |
| 同目录 `config.json` | **必需**（`port` + `faker`） | 不需要 |
| 依赖 | Qt 运行库 | 无 |
| 产物 | `<file>.dec_` → 覆盖 | `<file>_dec` → 覆盖 |

两者共同点（也是适配层真正依赖的契约）：自己判断头 3 字节是否加密；产物都是
**先落临时文件再 `remove + rename` 就地覆盖**；单文件模式不打任何输出。

> **关于随包分发**：`dec.exe` 是第三方二进制，本次随包的那份来自 `price-tool`
> （已在贵司环境验证、cmd 版无 Qt 依赖）。TCP 版若要用，需连同 `config.json`
> 一起放进去 —— 里面的 `faker` 进程名属于贵司信息安全策略，应由管理员决定。

### 其它配置项（可选）

| 环境变量 | 含义 |
|---|---|
| `WM_LDDEC_EXE` | 显式指定 dec.exe 路径（或其所在目录），优先级高于自动搜索 |
| `WM_DLP_ENABLE` | `0` / `off` / `false` / `no`（**不区分大小写**）一键关停整个解密通道；不设即启用 |
| `WM_DLP_DECRYPT_CMD` | 想接**别的**解密器时用，命令模板如 `"…{src}" "{dst}"`（填了它就**只**用这条） |
| `WM_DLP_TIMEOUT` | 单通道超时秒数（默认 30；LDDec 通道默认 60），**对内置链同样生效** |
| `WM_DLP_BUDGET` | 单个文件的解密**总预算**秒数（默认 120，覆盖各通道重试；`0` / 负数 = 不限）。总闸，防「拖 20 个加密文件卡几十分钟且关不掉」 |
| `WM_DLP_MAX_BYTES` | 明文**总量**上限字节（默认 4 GB）：一次性拖入几百个大文件时防撑爆磁盘 |
| `WM_DLP_MAGIC` | 加密魔数（十六进制，默认 `88 7d 1c`）；配错会在日志里留一行 `[WARN]` |
| `WM_DLP_TRACE` | `1` / `on` / `true` / `yes` 打开**解密跟踪**：每个文件的每条通道「尝试 / 成功 / 失败」与耗时写进 `runtime-<pid>.log`。排查「到底哪条通道解的、单文件花多久」时用，默认关闭（不留任何输出） |

自动搜索顺序：`WM_LDDEC_EXE` → 程序目录下 `LDDec/`、`tools/LDDec/`、程序目录本身、
`tools/lddec/`。

**想知道具体是哪条通道解的、各花多久**，两条路（都不需要装 Pillow / PyMuPDF）：

```bat
rem ① 用打包好的 exe：设一次环境变量再双击，看 runtime-<pid>.log
set WM_DLP_TRACE=1
水印工具.exe
```

```bat
rem ② 用源码逐通道强制单跑（连"整条链会走哪条"也一起给出）
<PY> tools/probe_dlp_channels.py "D:\Desktop\PLM验收单.pdf"
```

`tools/probe_dlp_channels.py` 只用标准库；拷到内网时最少带两个文件 —— 它和
`wm/dlp.py` 放同一目录即可直接跑。

**无论哪种解密器，交给它的永远是临时目录里的密文副本，不是原文件** —— 所以"就地
覆盖"语义（LDDec 正是如此）覆盖的也只会是一份副本。

### 四条铁律

1. **绝不覆盖 / 改写原文件**（沿用项目硬契约）：原文件全程只读。
2. **明文只落受控临时目录**（`tempfile.mkdtemp`，仅当前用户可访问），移出列表 /
   清空 / 关窗时逐个删除，进程退出由 `atexit` 兜底整删。
3. **输出命名仍按原路径**：`原名_水印版.扩展名` 落在原文件旁边，绝不会写进临时目录。
4. **不做进程伪装**：不改名、不注入、不冒充白名单进程名。系统读取通道只是让
   **系统自带的** `cmd.exe` / `powershell.exe` 去读文件 —— 驱动按进程决定是否返回
   明文，没授权时读到的仍是密文，会被判为"解密失败"。能否解密完全由管理员的策略
   决定，工具不绕过任何策略。

> 最省事的正道仍是**把 `WatermarkTool.exe` 加进加密软件的信任进程白名单** —— 那样
> 驱动自动返回明文，工具**零配置**即可处理，输出文件也会被自动加密。
> 项目分析与集成评估见 `docs/integration-lddec.md`。
